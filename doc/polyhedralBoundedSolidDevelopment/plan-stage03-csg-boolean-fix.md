## 3. Design conditions (non-negotiable invariants)
These conditions reflect what is correctly implemented with
respect to Mäntylä 1988. No change at this stage can break them.
### 3.1 Data structure invariants (chapters 10 and 13 of MANT1988)
- Each half-edge has its correct pair (twin) (`rightHalf`/`leftHalf`).
- Each face has at least one loop; each loop forms a closed cycle of
  half-edges via `nextHalfEdge`.
- Vertices and edges are shared correctly between faces.
- `PolyhedralBoundedSolidValidationEngine.validateIntermediate(solid)`
  must happen for all solid generated by successful operations.
- The Euler characteristic `V - E + F = 2S` (with S = number of shells)
  must be maintained.
### 3.2 Pipeline aligned with Mäntylä (chapter 15 of MANT1988)
- **setopgenerate** (`_PolyhedralBoundedSolidSetIntersector`): vertices
  of intersection projected to the receiving plane, parametric order
  stable (`IntersectorParametricOrderingTest`), weld post-intersect
  (`IntersectorWeldTest`).
- **setopclassify** (`_PolyhedralBoundedSolidSetClassifier` +
  `_PolyhedralBoundedSolidSetVertexFaceClassifier`): V/F and V/V classifiers
  aligned with Table 15.3. Null edge types (STRUT_A, STRUT_B,
  PARALLEL) correctly produced by `separateEdgeSequence` and
  `flipNullEdgeOrientationForOpenSide` (`VertexVertexEndpointRecoveryTest`,
  `VertexFaceClassifierCoplanarTest`).
- **setopconnect** (`_PolyhedralBoundedSolidSetNullEdgesConnector`):
  `scanjoin` (Program 15.13 literal), `sgetnextnulledge` (Program 15.14
  literal), `cutA`/`cutB` with lkemr/lkef depending on loop type
  (`SetOpConnectScanJoinTest`, `SetOpConnectNoLooseInvariantTest`).
- **setopfinish** (`_PolyhedralBoundedSolidSetFinisher`): invariant of
  face counters (`SetOpFinishInvariantsTest`), `sanitizePairedFaces`
  fallback must remain at 0 for all current cases.
- **preflight**: `weldCoincidentVertices` + `validateBooleanInputs` before
  of all operations (`PolyhedralBoundedSolidPreflightTest`).

## 11. Esquema bloqueante temprano (fail-fast pipeline)

### 11.1 Motivation
Currently, when an early phase of the pipeline produces data
invalid (degenerate vertices, non-coplanar faces, non-closed loops),
the error silently propagates until producing an incorrect result
or empty in the Connect/Finish phases. This makes the diagnosis
difficult: the visible fault (EMPTY or BLACK_FACES) is far from its cause
real.
Stage 3 introduces a **blocking validation scheme** between phases:
If a phase detects an error condition, it throws an exception that aborts
the complete pipeline. The tests must catch that exception and classify
the motif as `EXCEPTION` instead of `EMPTY` or `INVALID`.
### 11.2 Blocking points by phase

| Phase | Lock condition | Suggested exception | Origin class |
|------|---------------------|--------------------|-----------------|
| **Preflight (entry)** | Non-coplanar face (error > `coplanarDotTolerance`) | `IllegalArgumentException` | `PolyhedralBoundedSolidSetOperator.validateBooleanInputs` |
| **Preflight (entry)** | Almost coincident vertices without weld (distance < `epsilon()`) | `IllegalArgumentException` | idem |
| **Generate** | Intersection vertex outside the receiving plane (error > `bigEpsilon` after snap) | `IllegalStateException` | `_PolyhedralBoundedSolidSetIntersector.addArcToExistingFace` |
| **Classify** | `separateEdgeSequence` reaches cycle limit (cycle detection triggers) | `IllegalStateException` | `_PolyhedralBoundedSolidSetVertexVertexClassifier` |
| **Connect** | `looseA != 0 || looseB != 0` at the end of the main loop | `IllegalStateException` | `_PolyhedralBoundedSolidSetNullEdgesConnector.setOpConnect` |
| **Finish** | `sanitizePairedFaces` fallback is activated (counter > 0) | `IllegalStateException` | `_PolyhedralBoundedSolidSetFinisher` |
### 11.3 Implementation strategy
1. **Do not modify the existing preflight lock**: `validateBooleanInputs`
   already launches `IllegalArgumentException`. Verify that the message is
   descriptive enough for diagnosis.
2. **Add blocking on Connect**: currently the `looseA == 0` invariant
   It is documented but no exception is thrown. Add:   ```java
   if ( looseA != 0 || looseB != 0 ) {
       throw new IllegalStateException(
           "setOpConnect: loose ends after main loop: looseA=" + looseA +
           " looseB=" + looseB + " — null-edge ordering failure");
   }
   ```
This converts current EMPTY cases to `EXCEPTION` with clear message.
   **Precondition**: first verify with the complete suite that no
   ✅ Current case has looseA/looseB != 0 at the end of the loop.
3. **Add lock on Finish**: when `sanitizePairedFaces` is activated
   (count > 0), raise to `IllegalStateException`. The `SetOpFinishInvariantsTest`
   already verifies that the counter is 0 for all current cases, so
   that this lock should not break any existing tests.
4. **The 40×4 matrix test catches exceptions**: the test
   `KurlanderMotif4OperationMatrixTest` has try/catch around each
   `setOp`. Cases that previously returned EMPTY or INVALID should now return
   EXCEPTION with a stack trace that points to the exact phase of the failure.
### 11.4 Diagnostic value of the blocking scheme
With the blocking scheme:
- **EMPTY** becomes a legitimate result only when the intersection
  geometric is empty (no null edges generated). Any other EMPTY is
  now an exception in Connect.
- **INVALID** only occurs if post-operation validation fails, which
  indicates a bug in Finish or in the topology.
- **EXCEPTION** points directly to the phase: the message identifies whether
  was preflight, generate, classify, connect or finish.
The diagnosis of Phase 3 of the plan (§6.3) is simplified: compare the
exception message from cases ❌ with behavior from cases ✅.
### 11.5 Cases where blocking might be too strict
- **Non-coplanar faces in polygonal approximation solids** (e.g. the
  sphere): preflight may reject valid solids due to rounding error.
  See §12 for the correct treatment of these cases.
- **looseA != 0 by theoretical design**: Mäntylä §15.7 admits that in
  `INTERSECTION` connector may leave A-loose loose. See
  `SetOpConnectNoLooseInvariantTest` — the test already documents this case as
  `@Disabled` rightly so. The lock must be conditional on the operation:
  only throw exception if `looseA != 0 && op != INTERSECTION`.

## 12. Handling numerical errors and approximation
### 12.1 Numerical context of the pipeline
The CSG pipeline uses `PolyhedralBoundedSolidNumericPolicy.ToleranceContext`
for all geometric predicates. The scaled values ​​are:
| Field | Formula (with `scale = diagonalSize(solid)`) | Typical value (scale=1) |
|-------|------|------|
| `epsilon()` | `VSDK.EPSILON × scale` = `1e-6 × scale` | `1e-6` |
| `bigEpsilon()` | `10 × VSDK.EPSILON × scale` | `1e-5` |
| `unitVectorTolerance()` | `10 × VSDK.EPSILON` (fixed) | `1e-5` |
| `coplanarDotTolerance()` | `100 × VSDK.EPSILON` (fixed) | `1e-4` |
| `unitIntervalTolerance()` | `clamp(bigEps/scale, 1e-5, 1e-3)` | `1e-5` |
The context is automatically scaled by the size of the largest solid
(`forSolids(A, B)`). For the Kurlander bowl (external radius ≈ 0.7):
`scale ≈ 1.4`, `epsilon ≈ 1.4e-6`, `bigEpsilon ≈ 1.4e-5`.
### 12.2 Polygonal approximation problem for spheres
The Kurlander bowl is generated as:
1. `esfera exterior` SUBTRACT `esfera interior` (layers of polyhedra)
2. Result INTERSECTION `cilindro` → final bowl
The sphere is **approximated by polyhedra** with `N` divisions. every face
triangular/quadrilateral sphere is **almost planar** but not exactly
planar, since the vertices are on the surface of the theoretical sphere (or
on the approximation polyhedron).
This situation produces faces where the planarity residual is in the range
`(epsilon, bigEpsilon]`. The current preflight launches `IllegalArgumentException`
if a face exceeds `coplanarDotTolerance = 1e-4`. The faces of the sphere
discretized are below that threshold, so they **currently pass**.
However, after CSG operations, the faces created by the Splitter
can inherit vertices from original multiple faces, and the remainder of
planarity can grow. This explains the NON_PLANAR cases (motifs 22 and 23).
### 12.3 Rules for interpreting planarity errors
| Planarity residual | Interpretation | Action |
|------------------------|----------------|--------|
| `< epsilon` | Planar within numerical noise | Accept without question |
| `[epsilon, bigEpsilon]` | Gray area: normal polygonal approximation | Accept; register with `VSDK.reportMessage` in debug mode |
| `(bigEpsilon, coplanarDotTolerance]` | Suspected but tolerated by preflight | Always record; investigate if it affects classify |
| `> coplanarDotTolerance` | Real error: non-planar face | Block pipeline (preflight throws exception) |
The preflight must distinguish between "polygonal approach face" (areas
accepted grays) and "genuinely non-planar face" (block). For this
stage, the criterion is the current threshold (`coplanarDotTolerance`); if they
tests reveal which gray zone cases cause downstream failures, it can be
set the threshold to `PolyhedralBoundedSolidNumericPolicy`.
### 12.4 Impact analysis of numerical errors in the pipeline
For ❌ motifs, Phase 3 should investigate whether the error comes from a
propagation chain:
```
weak numerical precondition (gray zone)
  → face accepted by preflight
  → generates an intersection vertex with high residual
  → snap-to-plane introduces additional error
  → the V/V classifier sees ambiguous geometry
  → a tangential null edge is generated incorrectly
  → Connect fails (EMPTY) or Finish produces BLACK_FACE
```

**Diagnosis by propagation**:
For a specific ❌ motif:
1. Measure the maximum planarity residue of A and B before `setOp`
   (using `PolyhedralBoundedSolidValidationEngine`).
2. Record the distance of the intersection vertices to the receiving plane
   before and after the snap (in `_PolyhedralBoundedSolidSetIntersector`).
3. Check if any vertex is in the `(epsilon, bigEpsilon]` zone and
   if that vertex participates in any problematic null edge.
### 12.5 Numerical regression tests
To ensure that epsilon settings do not break behavior
current:
- **`PolyhedralBoundedSolidNumericPolicyTest`**: existing tests of the
  numerical policy (already in the suite). They must remain green.
- **Operand planarity test**: new test that verifies that, for
  all 40 motifs, the maximum planarity residue of A and B is
  below `coplanarDotTolerance` before `setOp`. If any reason
  If this check fails, it is known that the current preflight would reject it.
- **Pre/post snap residual comparison test**: for motif 0 and a
  ❌ representative motif, record waste and ensure that the snap
  it does not increase the error in an unacceptable way.
### 12.6 Epsilon adjustment: when and how
**When it is allowed to adjust epsilon at this stage**:
- If a test in §12.5 shows that the current `bigEpsilon` passes
  errors causing Classify to fail (measured value > bigEpsilon in
  intersection vertices).
- If the propagation analysis shows a demonstrable causal chain between
  a residue of planarity in the gray area and a failure in Finish.
**How to adjust**:
- Modify `PolyhedralBoundedSolidNumericPolicy.fromScale()` to change
  the multiplication factor of `bigEpsilon` (currently `10 ×`).
- Any adjustment must be accompanied by a specific test that justifies it
  and it should not break any existing tests.
**When not to adjust epsilon**:
- As a substitute for a correct fix in the algorithm (e.g. do not increase
  `coplanarDotTolerance` to mask a real NON_PLANAR).
- If the impact on the 305 existing tests has not been measured.

### 14.3 Patrones cruzados observados (§2.3 del plan)

1. **EMPTY in A-B but OK in B-A**: motifs 9, 19, 25, 34, 35, 38, 39.
   The bowl SUBTRACT motif produces EMPTY but the SUBTRACT bowl motif produces OK.
   Hypothesis: the orientation of the null-edges in sonea favors B as the first
   argument. The problem is asymmetric in the ordering of the Classifier.
2. **OK in A-B but EMPTY/BLACK_FACES in A∩B**: motifs 3 (AiB=BLACK), 22
   (AiB=EMPTY), 26, 37 (AiB=EMPTY). Intersection fails where subtraction works.
   Hypothesis: Finish phase for INTERSECTION (`inda = sonfa.size()`) discards
   the faces of A that the subtraction includes; an error in the pairIndex causes
   sonfb is empty.
3. **BLACK_FACES in A-B but OK in AiB**: motifs 6, 8, 13, 17, 20. The intersection
   works correctly but subtraction produces faces with inverted normals.
   Hypothesis: `revert(B)` on Finish reverses correctly for INTERSECTION
   but introduces additional investment in SUBTRACT for certain orientations
   relative bowl-motif.
4. **B-A shellCount=1 instead of 2**: 19 out of 28 OK cases in B-A have shellCount=1.
   The bowl should divide the motif into two related components; if shellCount=1
   It is because the two portions were connected by an incorrect cutting face.
   (or the cut face was not created). See §14.4.
5. **Motif 24, 27, 29, 32, 33, 36 totally EMPTY** (all ops): the bowl and the
   motif are positioned such that the geometric intersection is minimal or the
   Classifier produces zero null-edges for all orientations.
### 14.4 Root cause B-A shellCount=1 (new hypothesis)
Invariant §4 says that B-A must produce shellCount=2. The table shows that
only 9 of 28 OK cases in B-A satisfy this invariant.
**Main hypothesis**: when the motif-star intersects the bowl in two rings
(one on the inner concave face and another on the outer convex face), the phase
Connect produces two cutting faces (one per ring). If both cutting faces
remain in the same shell, the result has shellCount=2. But if the Classifier
does not distinguish the two rings (because the star crosses the bowl in a single ring
continuous), Connect produces only one slice face and the result has shellCount=1.
**Geometric difference between shellCount=1 and shellCount=2**:
- shellCount=2: the star-motif crosses both surfaces of the bowl (the outer sphere
  and the inner sphere of the hemisphere), producing two intersecting rings.
- shellCount=1: the motif-star only crosses one of the two surfaces, producing
  a single intersecting ring (the motif is completely inside or outside).
Motifs with shellCount=2 (0, 2, 6, 8, 10, 11, 15, 17, 21) are the ones that cross
both surfaces of the bowl. This is the correct geometry that the invariant assumes.
